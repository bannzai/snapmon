# 0001. 技術スタック: Flutter + Flame × Firebase × Claude API × Jev

## Status

Accepted

## Context

snapmon は、撮った写真の被写体がモンスターになってターン制で戦うゲーム。配信先は iOS / Android / Web (立ち上げ設定)、目的は「バズらせる」ことで、その後すぐにストアへ申請できる状態にする (作るかの判断: https://github.com/bannzai/snapmon/issues/2#issuecomment-6308773377 )。仕様で決まっているのは [DIRECTION.md](../DIRECTION.md)「ゲームの仕様」のとおりで、ここでは次の制約が効く。

- 同じユーザーの同じ被写体を二重に登録しない判定と PvP に、ユーザーの識別とサーバー側のデータが要る
- 名前・図鑑の文章は LLM、属性・技・ステータスは master ファイルと Jev で決める (bannzai の返答)。どちらも API キーをクライアントに置けない
- Gemini API は利用者を 18 歳以上に限る規約があり、ポケモン風の見た目は子どもが使う可能性が高い ([PROJECT.md](../PROJECT.md)「設計の制約」)
- Cloud Storage for Firebase と Cloud Functions は Blaze プラン (従量課金) が要る (同上)
- 他人のモンスター (他人の写真から作った物) を見せる PvP は、App Store / Google Play の UGC 要件 (フィルタ・通報・ブロック・連絡先) の対象になる (同上)
- オンデバイスの画像分類 (ML Kit) の Flutter プラグインは Web 非対応 (同上)

## Decision

| レイヤ | 決定 | 理由 |
| --- | --- | --- |
| クライアント | Flutter + Flame | 立ち上げ設定で確定。bannzai/kashakeibo (Flutter × Firebase のストア配信) と bannzai/egg_clicker (Flame) の資産を流用する |
| 写真の理解と文章の生成 | Claude API (vision)。Cloud Functions (gen2) 経由で呼び、API キーは Secret Manager に置く。未成年向けの安全策として、システムプロンプトに子ども向けの制約 (暴力・性的・差別的な表現を出さない、写真の人物の特徴を書かない) を入れ、名前・図鑑の文章が AI 生成であることをアプリに表示し、生成の前後でコンテンツフィルタ (下の「不適切な画像」と、生成した文章の禁止語の検査) を通す | Gemini API の 18 歳以上の制約を避ける。Anthropic は未成年が触れる製品に安全策 (年齢確認・コンテンツフィルタ等の技術的な対策、子どもの安全向けのシステムプロンプト、法令順守、AI と対話していることの開示) を条件に認めている ( https://support.claude.com/en/articles/9307344-responsible-use-of-anthropic-s-models-guidelines-for-organizations-serving-minors )。年齢確認は「use case に合った技術的な対策」の例示のひとつ ("may include, but are not limited to") で、下の「対象年齢」の行の年齢の確認と、フィルタとプロンプトで満たす。クライアント直呼びにすると生成回数の上限を強制できず LLM 原価の上限を守れない (kashakeibo ADR 0001 と同じ判断)。Claude には被写体の構造化した説明 (何か・色・素材・大きさ・硬さ等)・名前・図鑑の文章・装飾のパラメータ (下の「モンスターの見た目」の行の目・手足・属性のオーラ・輪郭線) を JSON で出させる |
| 属性・技・ステータスの判定 | Jev (TypeSafe の判定 API)。Claude の構造化した説明を state にし、master の属性ごとの当てはまり (Noul)、ステータスの段階 (Score)、技の選択を 1 リクエストで判定する。技は、当てはまった属性の技 (master とその場で作った定義の両方。属性ごとに 255 件以下) を候補にし、属性ごとに 1 つの Choice で「最も合う技」を選び、覚える技の一覧は属性ごとの Choice の結果と master のレベル帯から組む (Choice の criteria は 255 件まで・返るのは 1 件のため、技全体から一度に選ばない)。同じく Cloud Functions 経由 | bannzai の返答 (早い・安い)。Jev の入力は文字列だけのため ( https://docs.typesafe.ai/models.md 「Jev reads natural-language text」)、画像は先に Claude で文字列にする。1 リクエストに複数の問いを入れられ、問いの型は Noul・Choice・Score の 3 つ ( https://docs.typesafe.ai/api.md 。`state` は「The content all questions in this request refer to」。Choice の `criteria` は OpenAPI スキーマで `maxProperties: 255`、"Identifies a question that selects one of the choices in criteria")。Claude の返答は同じ写真でも揺れるため、最初に得た構造化した説明を生成レコードに保存し、ステータスはその保存した説明と Jev の段階から決定的に計算する (個体値の擬似乱数の seed は保存した説明のハッシュ)。計算の手順には版番号を付けてモンスターに保存し、後で式を変えても既存のモンスターの値は変えない (既存アプリの「生成物が変わる」不満への答え) |
| master に無い属性・技 | Jev の当てはまりがすべて閾値未満の時だけ、Claude に master のスキーマ (名前・説明・属性・威力・PP。相性は含めない) で新しい定義を 1 件提案させ、サーバーが値域 (威力・PP の上下限) と、名前・文章と同じ禁止語・他社の名称 (ポケモンの技名・タイプ名) の検査を通して `definitions/` に版付きで保存する。保存の前に既存の定義 (名前の完全一致と、Jev の Noul で「同じ意味の定義があるか」) と照らし、あれば既存を使う。保存は上限のカウンタと同じ Firestore のトランザクションで行う (トランザクションが防ぐのは名前が完全に一致する重複で、同じ概念の別名は上の Jev の照合で防ぐ)。新しい属性の相性は既存の全属性と等倍に固定し (Claude は相性を決めない)、相性表は全体で 1 つの版を持って対戦時点の最新の版を両者に適用する (個体の属性・技・値だけが不変)。master (属性・技・相性表・分類) はアプリに同梱せず Firestore の `master/{version}` に置き、クライアントは起動時と対戦の前に最新の版を取得する。`definitions/` と `master/` は認証済みユーザーが読める (他人のモンスターが参照する定義を端末で解決するため)。相性表の更新は agent が master を直す PR と、Functions のデプロイで行う。上限は属性 24 種・技 2,000 件で、超えたら Jev の当てはまりのスコアが最も高い既存の定義を使う | bannzai の返答 (「登録したときに既存のカテゴリにならず属性や技が相応しいと判断した場合はそのときに作る」)。Claude は判定 (選ぶ) を代替せず、候補が無い時の提案だけを担う。相性表の版を 1 つにしないと、版の違う 2 体の対戦でどちらの相性表を使うかが定まらず、端末で計算する非同期 PvP の結果が揺れる |
| 同じ被写体の判定 | 「同じ被写体」は同じ個体 (同じマグカップ) を指し、同じ種類の別の物 (別のマグカップ) は別の被写体として登録できる ([DIRECTION.md](../DIRECTION.md)「決めたこと」)。生成の状態遷移に classify (Claude の後) と dedupe (classify の後・judge の前) の段階を置く。classify は Cloud Vision の Label と Claude の説明を state にして master の「物の分類」を Jev の Choice で決め、上位 3 件の分類 ID を保存する。dedupe は、そのユーザーの既存のモンスターと判定待ちのレコードのうち分類 ID (上位 3 件のどれか) が重なるものをすべて対象にし、20 件ずつに分けて (1 リクエストの問いの単位) 新しい説明と各モンスターの保存済みの説明を Jev に渡して「同じ個体か (色・傷・付属物・置かれた場所の一致)」(Noul) を判定する。古い個体も対象に残す。閾値以上の既存があれば終了状態 duplicate (既存の monsterId を返す) にし、以後の有料の API は呼ばない。同じ uid の生成は `users/{uid}` の生成中ロック (予約と同じ 10 分の lease。saved / duplicate / rejected で解放し、判定待ちになった時も解放する) で直列にし、処理中のレコードの画像ハッシュとも突き合わせる | bannzai の返答 (二重登録の判定は master + Jev)。Claude の説明は同じ物でも揺れるため、候補の絞り込みも最終判定も文字列の一致を使わず、分類も完全一致ではなく上位 3 件の重なりで絞る (角度の違いで分類が変わる見逃しを減らす)。直列にしないと連打で両方が判定を通って二重に保存・課金される |
| モンスターの見た目 | 写真から切り出した被写体の画像に、Claude が返す装飾のパラメータ (目・手足・属性のオーラ・輪郭線) を Flame で重ねる ([DIRECTION.md](../DIRECTION.md)「決めたこと」2026-10-22 の行で、AI 生成のイラストから変更)。切り出しは自動 (AI を使ってよい) と、クライアントでユーザーが手で範囲を決める経路の両方を用意する。どちらの経路でも、クライアントが送るのは元の写真と範囲のマスク (手動の時はユーザーが決めた範囲、端末内で自動のマスクを作る時はその結果。マスクをサーバーで作る時は写真だけ) で、切り出した画像そのものは受け取らない。切り出しの適用は常にサーバーが行い、SafeSearch と顔の検出を通った元の写真から切り出す (他人に見せる `art.png` が検査を通っていない画像にならないようにする)。切り出しは状態遷移の cutout の段階 (safesearch の直後・claude の前) で行い、被写体を切り出せない写真はそこで rejected にして有料の API を呼ばない。切り出した画像は cutout の段階で本人だけが読める `users/{uid}/generations/{requestId}/cutout.png` に置き (再試行で切り出しをやり直さないため)、saved の時に `monsters/{monsterId}/art.png` へ移して作り直さない。選定を ADR 0002 に残すのは、自動のマスクを作る場所 (端末内の OS の機能か・サーバー側の AI か)・使う API・原価・Web 版での経路で、生成の実装 (#13) で書く。装飾のパラメータと描画の版もモンスターに保存する | 「被写体に似ている」が差別化の核で、切り出しが最も似ていて、1 体あたりの費用も生成結果の揺れも無い。生まれた時の画像を保存しないと「生成物が変わる」不満そのものになる |
| 認証 | Firebase Authentication の匿名ログイン → Sign in with Apple / Google へのアカウントリンク。Firebase App Check を必須にする (Apple: App Attest / DeviceCheck、Android: Play Integrity、Web: reCAPTCHA Enterprise。 https://firebase.google.com/docs/app-check が各プラットフォームの provider として挙げる名称) | 登録なしで使い始められ、二重登録の判定と PvP に要る uid が最初から取れる。引き継ぎはリンクで行う。匿名ログインは uid を作り放題のため、App Check で正規のアプリ以外からの呼び出しを弾く |
| 対象年齢 | 13 歳以上。初回起動の最初の画面で年齢の確認 (生年月の入力) を行い、それより前に Firebase Auth・Analytics・App Check を初期化しない (識別子を取らない)。13 歳未満は使えない。確認の結果はサーバー側でも検査する: 年齢の確認の後に匿名ログインし、Functions (`confirmAge`) が生年月から 13 歳以上であることを検証して Auth のカスタムクレーム `ageVerified: true` を付ける。生成・PvP・バトル結果の Functions と Storage・Firestore の Rules はこのクレームを必須にし、クレームが付くまでクライアントは Analytics を初期化しない。Play Console の対象年齢は 13 歳以上で申告する。COPPA 等の順守の方針はプライバシーポリシーに書く | [DIRECTION.md](../DIRECTION.md)「決めたこと」の対象年齢の行 (COPPA の保護者の同意と Google Play の Families のポリシーの出典はそちら)。COPPA の FAQ D.4 は mixed audience の年齢確認の条件を "does not collect personal information from any visitor prior to collecting age information" とし、C.5 は persistent identifiers (unique device identifier) を personal information に含めるため、初期化の順序を縛る。本アプリが COPPA の「子ども向け (directed to children)」に当たるかは bannzai の判断待ち (当たるなら 13 歳未満を締め出せず、保護者の同意の仕組みが要る。DIRECTION.md の同じ行) |
| DB | Firestore | ユーザーごとの図鑑・手持ち・PvP で見せる相手のデータを置く。Flutter との組み合わせは kashakeibo で実証済み。`users/{uid}/monsters`・`users/{uid}/generations`・`definitions`・`users/{uid}/battles` はクライアントから書けず (Security Rules で deny)、Functions (Admin SDK) だけが書く。クライアントから書けるのは手持ちの選択 (`users/{uid}/party`。Rules で「自分の `monsters` に存在する ID を 3 件まで」に限る) と設定だけ。非同期 PvP の勝敗は端末で計算し、サーバーは検証しない (レベルは勝敗に関係なく 1 戦で +1 のため、Functions は 1 日の戦闘回数の上限 50 戦 (原価と不正の抑えのための agent の値) と 1 戦あたり +1 だけを検証して書く)。レベル加算は冪等にする: バトルの開始時に Functions が `battleId` を発行して `users/{uid}/battles/{battleId}` を未完了で作り、結果の送信はそのトランザクションで完了状態を確認して未完了の時だけレベル加算と完了記録を同時に書く。同じ `battleId` の再送は加算せず既存の結果を返す |
| 画像ストレージ | Cloud Storage for Firebase (Blaze) | 元の写真は `users/{uid}/photos/{requestId}` に置き、Security Rules で本人だけ読める・書けるようにし、サイズ (4 MB 以下) と Content-Type (image/jpeg・image/png) を制限する。rejected・duplicate で終わった生成と、アカウント削除で元の写真を消す (消せなかった分は Cloud Tasks の再試行で消す)。切り出した被写体の画像は `monsters/{monsterId}/art.png` に置き、認証済みユーザーが読める (PvP と共有カードで使う)。書き込みは Functions だけ。他人に見せるのは切り出した被写体の画像 (写り込んだ私物を含む) と装飾のパラメータ・名前・属性・技・ステータスで、元の写真は見せない (共有カードにも入れない) |
| サーバーコード | Cloud Functions (gen2)。生成 (SafeSearch → 被写体の切り出し → Claude → 同じ被写体の判定 → Jev → 保存)、PvP の相手の取得、戦闘回数の上限とレベル +1 の検証と保存、アカウント削除。再試行は Cloud Tasks のキュー | API キーをクライアントに置かない。Flutter Web でも同じ経路で動く。生成は冪等にする: クライアントが生成要求ごとに作る UUID (再試行でも同じ値を送る) を冪等キーにし、`users/{uid}/generations/{requestId}` を Firestore のトランザクションで予約 (期限 10 分の lease 付き。生成の Functions のタイムアウトは lease より短い 5 分にし、元の実行と再試行が同時に API を呼ばない。期限切れの予約は Cloud Tasks の再試行が引き継ぐ) してから、状態を uploaded (クライアントが Storage に置いた写真のパスと、手動で切り出す時は範囲のマスクを記録。再試行はこの写真を読む) → safesearch → cutout (被写体の切り出し。切り出せなければ rejected) → claude → classify → dedupe → judge → saved と進める (終了状態は saved / duplicate / rejected / failed。Jev を呼ぶ classify・dedupe・judge のどれかで Jev が答えない時は待ち状態 pending_judge で保存し、Cloud Tasks の再試行が続きから処理する。再試行は 1 時間おきに最大 24 回で、超えたら failed にしてクライアントに撮り直しを案内する)。Functions が受け取った画像のハッシュとマスクのハッシュの組を補助キーにし、同じ組の完了済みレコードがあればその結果を返す (自動の切り出しで rejected になった写真を、手で範囲を決めて送り直す経路を塞がないため)。タイムアウト後の再試行は同じレコードを読んで済んだ段階を飛ばし、有料の API 呼び出しを繰り返さない。「同じ被写体」の判定は上の「同じ被写体の判定」の行 |
| 不適切な画像・人物 | Claude の生成の前に Cloud Vision の SafeSearch (露骨・暴力) と Face Detection を同じリクエストで実行し、露骨な画像と顔が写る画像は生成しない。Label Detection も同じリクエストに入れ、ラベルを「物の分類」の候補 (上の「同じ被写体の判定」) に使う (SafeSearch はこの条件で無料になるが、Label 自体が有料のため費用は変わらない。ラベルを分類に使うことが入れる理由)。PvP の通報・ブロックは Firestore に記録し、通報されたモンスターは相手の候補から外す | ストアの UGC 要件と、本人を判別できる写真が個人情報に当たること ([PROJECT.md](../PROJECT.md))。Cloud Vision の料金は月 1,000 ユニットまで無料、1,001〜5,000,000 ユニットは 1,000 ユニットあたり $1.50 で、SafeSearch は Label Detection と同じリクエストなら無料 ( https://cloud.google.com/vision/pricing の SafeSearch の行「Free with Label Detection, or $1.50」。2026-10-21 に確認)。Face Detection に同じ無料の条件は無く、1,000 ユニットあたり $1.50 のまま |
| 原価の上限 | uid ごとに 1 日の生成回数の上限 (値は実装時に決めて利用規約と揃える)、プロジェクト全体で 1 日の生成数の上限 (Functions が Firestore のカウンタで判定)、GCP の予算アラート (`/gcp-alert-setup` skill) | 匿名ログインでは uid の上限だけでは原価を抑えられないため、App Check と全体の上限と予算アラートの 3 つで守る |
| Analytics | Firebase Analytics (BigQuery エクスポート) | 判定基準の計測元。Analytics 自体は無料だが、BigQuery エクスポートは BigQuery の料金 (無料枠あり。保存と問い合わせに課金) の対象 ( https://firebase.google.com/docs/projects/bigquery-export 「Your use of BigQuery is subject to BigQuery pricing, which includes limited no-cost use」)。エクスポート先のテーブルの保持期間を 90 日にし、集計は日次の集計テーブルに対して行って問い合わせの量を抑える |
| クラッシュ | Firebase Crashlytics | product-loop がクラッシュ数を読む。通知は #snapmon-notification へ |
| Web 版のホスティング | Firebase Hosting (同じ Firebase プロジェクト) | 本番の配布は、触れる版を見て公開に進むと決まるまで `workflow_dispatch` だけにする |
| 紹介ページ・法務ドキュメント | GitHub Pages (`docs/`) | リポジトリが public で追加のホスティングが要らない |
| 課金・広告 | 最初の版には入れない | 目的が「バズらせる」ため。後から RevenueCat で足せる |
| 環境 | prod のみ (`snapmon-prod`) | 1 人開発で dev 環境の運用コストが見合わない。開発中の検証は Firebase Local Emulator Suite と CI で行う |

## Consequences

- Firebase は Blaze プラン (従量課金) で始める。生成 1 体の原価は未試算。単価の出典: Claude の vision 入力はトークン換算 ( https://platform.claude.com/docs/en/build-with-claude/vision 、料金 https://platform.claude.com/docs/en/about-claude/pricing )、Jev は入力トークンだけに課金で jev-1.13.0 が $42 / 10 億トークン ( https://docs.typesafe.ai/models.md 「$42 per Btok」。出力トークンは現時点では無料: https://docs.typesafe.ai/api.md の `Usage.output_tokens` "Output tokens are currently free of charge.")、Cloud Vision は上の表。実装時に見本 20 件で実測して本 ADR の後続に書く
- サーバーコードが Cloud Functions に集まるため、デプロイ対象はアプリ (3 プラットフォーム) + Functions + Hosting + Pages になる
- 生成の待ち時間は、Cloud Vision → Claude → Jev の分類 → (候補がある時の) Jev の同じ被写体の判定 → Jev の属性・技・ステータスの判定の各 API 呼び出しと、被写体の切り出しの所要時間の合計になる。切り出しが API 呼び出しになるかは ADR 0002 で選ぶ手段による。同じ被写体の判定は候補の数に応じて複数回の呼び出しになり、master に無い時は Claude の提案と Jev の照合が加わる (既存アプリで褒められている「生成の速さ」を落とさないよう、計測して見直す)
- TypeSafe の課金の仕組み (前払いのクレジットか、切れた時の API の応答) は一次情報で未確認。Jev が答えない (HTTP エラー・タイムアウト) 時は Claude に判定を代わらせず (属性・技・ステータスの決め方を master + Jev に固定するため)、生成レコードを待ち状態 `pending_judge` で保存してクライアントには待ち状態を返し、Cloud Tasks の再試行が同じレコードを続きから処理する (回数の上限と failed への遷移は Decision のサーバーコードの行)。cutout (切り出した画像は中間のパスに残す) と Claude の段階は済んでいるため、復帰後に再課金は起きない。判定待ちのレコードは dedupe の比較対象に含める (同じ被写体の別の写真が通らないため)
- 登録時にその場で作った属性・技の定義は Firestore に版付きで保存し、モンスターには定義の ID と master の版を保存する ([DIRECTION.md](../DIRECTION.md)「決めたこと」)。master の更新で既存のモンスターの値・技を変えない
